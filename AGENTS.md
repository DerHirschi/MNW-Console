# Agent Guide — MNW Ship Probe

Autonomous data probe + control console for **Modern Naval Warfare (MNW)**.
Runs inside the game via the runtime AI scripting API (Level 2), piggybacked
onto the element scripts the game provably executes. Read this file before
editing anything. `README.md` covers usage; this file covers the engineering
knowledge and verified game facts.

## Repo Layout

- `ship_probe.py` — the in-game script. Module-level `_start_/_random_tick_/_stop_` hooks, `ship_probe_tick(host)` entry, `_Probe` class. Importable without the game (no side effects) — tests rely on this.
- `ship_probe_config.json` — deployed config; mirrors `_DEFAULTS` in `ship_probe.py`.
- `deploy.py` — deployer (inject/execute/package modes, verify/remove/purge-execute).
- `console.py` — external CLI over the JSON file protocol.
- `tests/` — plain `unittest`, NO external deps. Run: `python3 -m unittest discover -s tests -v`
- `README.md` — usage documentation.

No build system, no linting config. Python 3 only.

## How the Probe Runs (Architecture)

- The game **only executes element-bound scripts** (attached to ships/subs in missions). Standalone scripts are never instantiated.
- `deploy.py` appends a guarded block into `_random_tick_` of 8 proven scripts (PIGGYBACK_TARGETS in `deploy.py`):
  ```python
  # ship_probe piggyback v1
  try:
      import ship_probe
      ship_probe.ship_probe_tick(globals())
  except Exception:
      pass
  ```
- `ship_probe_tick(globals())` → leader election via `ship_probe.lock` (stale after 30 min) → `_Probe.begin()` (player detection + discovery) → `tick()` every `tick_delay` ticks.
- All output files go to the **first writable dir** of: `log_dir` (config) → script dir → cwd → HOME → /tmp.
- File protocol (JSON, no network): `ship_state.json` (probe→console), `ship_probe.json` (API discovery map), `ship_orders.json` (console→probe, `{"commands":[{"cmdid":N,...}]}`), `ship_results.json` (results keyed by cmdid), `ship_probe_log.txt` (tailable log), `ship_probe.lock`.

## Verified Game Facts (Level 2 Runtime API) — RESEARCH COST: HIGH, DO NOT RE-DERIVE

The game embeds Python for .NET. Two distinct API levels:

- **Level 1 = mission scripting** (`_P.*`, `_T.*`, `_Z.*`): runs once at mission load. NO tick hooks, NO runtime reads of ship state, `_mission_started` is built-in. Documented in `/home/masto/MNW-Mission-Builder/AGENTS.md`.

### Hard limits (do not re-test in-game)

- **The ContactManager/MergedContacts pipeline is a freeze source — gate EVERY read that touches it behind a config flag.** `ContactManager.MergedContacts` crashed with `IndexOutOfRange` (`merging.py`, 38x) in an early session. `read_contacts: false` alone was NOT enough: `read_sonar()` → `son.StrongestContact` also enters the same pipeline and **hung the Unity main thread** (whole game frozen at ~12s into a mission, host id 10; same code had passed in host 15 earlier — the hang is element/host-state dependent). **FIX (2026-08-17):** `read_sonar()` nutzt jetzt `GetContactIDs()` + `GetTrackerData()` (sicherer Tracker-Pfad, kein StrongestContact). `read_sonar:true` ist jetzt sicher und aktiviert. `read_contacts:true` auch aktiviert (Contacts via ContactManager sind separate Pipeline, funktioniert).
- **Freeze signature (read-only, don't re-derive):** probe log AND `Player.log` stop advancing at the SAME nanosecond, `mnw.exe` still burns ~150% CPU → a blocking call inside the probe's tick on the game thread. The game itself is frozen (not just the probe). Check: `stat -c %y` on both logs + `ps -o pcpu`. Last checkpoint line before the gap pinpoints the function (e.g. `cp: contacts done` with no `sonar done` = stuck in `read_sonar()`).
- **CALLING a method on a Unity-side CLR object from the probe can hang the game thread — `dir()`/`getattr` are safe, INVOKING is not.** On 2026-08-16 `discovery_run` froze the game at start: `GetKeys()` on the player's `mnw.Core.Bus.Controller` (and on its nested `.Controller`/`.Hub`) hung the Unity main thread during the START discovery (log ended at `clr_warmup ... High=ok`, no `discovery:` line). Removed the `GetKeys()` calls; the nested lookup now only does `getattr`. **Rule: in the probe, NEVER call methods on game objects — only `dir()`, `getattr`, and indexing fields/collections that are already live.**
- **`getattr` on UNVERIFIED fields of Unity objects can also freeze** — 2026-08-16 second start: even after removing `GetKeys()`, `getattr(inner_controller/hub, "_Registry"/"_Buses"/"_ComponentDict")` still hung the game at the same point (two freezes total). The `player_controller_probe` getattrs (Access, Hub, Controller, Scope, ScopeSelector, Interfaces) are VERIFIED freeze-safe; the `_*` field getattrs on the nested `.Controller`/`.Hub` were NOT. Fix: nested lookup is `dir()`-names-only. **Rule: only `getattr` members that were verified freeze-safe in a prior successful run; for everything new, dump `dir()` names first, then pick the exact field.**
- **Accessing `.Overloads` on a C# method/constructor from Python freezes the game.** 2026-08-17: `ss.TrackContact.Overloads` (where `ss.TrackContact` is a C# overloaded method) hung the Unity main thread. The game log stopped, process died. `.Overloads` is a reflection property that triggers internal .NET runtime enumeration — same category as calling methods on Unity-side CLR objects. **Rule: NEVER access `.Overloads`, `.GetOverload`, or any reflection/introspection property on C# methods/constructors from the probe. Instead, try each overload combination silently with `_try()`.**
- **Deploy copies the config from the REPO dir via `source_paths()`, not what you hand-edited in the game tree.** `sync_execute_tree`/`inject_package` read `ship_probe_config.json` next to `deploy.py`. If you scp a local config over the remote repo's config AFTER setting remote-only flags, the next deploy overwrites the game config with the local (test) values. Order matters: edit/verify the config in the repo where deploy runs, THEN deploy. Always re-check the deployed `_Source/ship_probe_config.json` after deploy (e.g. `cat` it) — the log line `config={...}` in `ship_probe_log.txt` shows exactly what the game loaded.
- **JSON: .NET structs (e.g. `System.Double`, `Vector3`) are not JSON-serializable** → `_json_default` fallback in `_atomic_write` (float-like → str). The old failure appeared as `TypeError: 333.857 is not JSON serializable` at the END of an otherwise-successful tick.

- **`m.Player` freezes the Unity main thread.** Detect player via `CoordinatesManager.Player` (int) / `PlayerGCID`; fallback `target_element_id` config. NEVER call `m.Player`.
- **No `clr` import at runtime** (`clr.AddReference` fails in the embedded interpreter). Resolve types via `g()` fallback chain: host globals → module globals → `__import__("mnw.*")`.
- **No `_P.*`/`_T.*` at runtime** — mission-scripting API is load-time only.
- **A second `.kyt` in `Var/Scripts/Packages/` breaks extraction** ("An item with the same key has already been added" + loading screen hang). Always inject into the existing scripting package (`find_scripting_package`: kyt whose manifest lists `_Source/*` or `_MNW/*` entries).
- **`ship_probe.py` IS re-extracted from the .kyt at launch (CORRECTS the "loose files survive" rule below):** 2026-08-16 the game overwrote the loose `Execute/_Source/ship_probe.py` from `hal_9025.kyt` at startup — several "deploy ok + game restarted" cycles kept running the OLD hash (e.g. `2916fa85…`). Deploy MUST be `--inject` (patch the kyt entry AND loose tree) and the authoritative verification is comparing the kyt entry's md5 against the loose `_Source/ship_probe.py` (a `--verify` mismatch on `_Source/ship_probe_config.json` is EXPECTED — see Re-patch bullet). `console.py`/tests are repo-only; never deployed.
- **Loose `Execute/_Source` files survive re-extraction** — the game does not reliably overwrite extracted files, so `sync_execute_tree` must always run after package injection; `--purge-execute` forces fresh extraction.

### Reading rules (consumer MUST follow)

- **State reads** → `ship_state.json` (player) / `ai_state.json` (AI). Poll at `state_every`-aligned cadence; a tick with `tick_delay:30` + `state_every:10` refreshes ~every 30 s wall-clock. Do NOT fabricate values for `None`/`err` fields — they mean the read is gated or absent.
- **Order results** → `ship_results.json` keyed by `cmdid`. Results akkumulieren über Ticks (fix 2026-08-17: alte Results werden gelesen und concateniert, nicht überschrieben). Bei `max_commands_per_cycle=10` und 12 Commands: Tick 1 verarbeitet 10, Tick 2 die restlichen 2 — beide landen im selben Array. **Aber:** immer noch last-writer-wins bei multi-host (Akula/Helo eigener Host). Für autoritative per-command Tracing: `ship_probe_log.txt` (`cp…` Lines).
- **Never call `m.Player`, never read `.Operator` on AI elements, never `Controller.Access[Type]` for a component the element may lack** (freeze/native-crash — see Hard limits). The probe already routes around these; consumers must not bypass the probe for live reads.
- **GQ is NOT observable** in `ship_state.json` (`_CurrentTensionLevel` is Diplomacy tension, not GQ). Bulkheads/lights/ciws are reprs only.

### Sending commands (consumer contract)

- Write `ship_orders.json`: `{"commands":[{"cmdid":N,"action":"…",…}]}`. **Atomic replace** (write tmp + `os.replace`) — the probe reads the whole file. `cmdid` must be **monotonically increasing** (probe dedupes via `last_cmdid`); a consumer may queue several in one file. Never append-only / never renumber an already-used id.
- Whitelist check: the probe returns `denied (not in allow_commands: …)` if the action isn't in the deployed config. Deploy-time control: `allow_commands` in `ship_probe_config.json` (repo + package + loose tree, see Re-patch warning above).
- `helm COURSE [EOT] [DEPTH]` — course deg, EOT in `Stop/AheadStd/Ahead13/AheadFull/AheadFlank`, depth m. Affects the PLAYER sub via `player_controller().Access[SteeringDiving]()`.
- `plot LAT LON` — sets a route; **in-game AUTOPILOT must be engaged** for it to steer. Plot targets **>5 km** away (close waypoints make the boat circle them).
- `ai-attack ID [--allow-untracked] [--domain X]`, `steer ID LAT LON [--speed K]`, `wc ID` — AI-side commands (domain = BaseCategory name). Check the per-command help in `console.py` `HELP`.
- `report` (ReportToHQ), `probe` (re-run discovery), `clear-plot`, `detected` (which AI track the player).
- Available but NOT in the deployed whitelist (must be added + re-deployed to use): `ns-dump`, `asg`, `ai-contacts`.

## Launcher Categorization (verified 2026-08-16, live-tested)

The WeaponController builds three category dictionaries per launcher from the **mounted weapon's DB `TargetCategory`** (resolved via `Core.Select(ElementCategory, MountedDatabaseID)`), NOT from the `MountedCategory` bits alone. `CollectFlags` iterates **`ElementCategory`** and keeps every `elementCat` where `(mountedCat & elementCat) == elementCat`, yielding the ElementCategory flag(s) of the launcher (e.g. Missile=128, Projectile=32, Torpedo=256). The DB row it then selects is keyed by that ElementCategory.

- **`CollectFlags(MountedCategory)`:** keeps every `ElementCategory` value where `(value & mountedCat) == value`. A Missile launcher (128) returns `[Missile]`, a Type-87 rack (Projectile=32) returns `[Projectile]`, a tube (256) returns `[Torpedo]`. Does NOT AND with `BaseCategory` values.
- **`CollectWeaponInformation(launcherIdx)`:** `flags = CollectFlags(ws.MountedCategory)` → for each flag: `Core.Select(flag, ws.MountedDatabaseID)` → get `TargetCategory` + `Range` → `AttackRangeInformation`. **`_BaseCategories[i]`** = the DB `TargetCategory` of the weapon mounted in that launcher. Empty launchers (dbid=0 → `Select` returns null) keep `TargetCategory=0` and get no category.
- **`Core.Database.Select(arg1, arg2)`:** `_Categories[arg1].Select(arg2)` — the `_Categories` dict is keyed by **`ElementCategory`**, so the lookup `Core.Select(Projectile, 99992902)` hits the `projectiles.msg` table. (Weapon tables: Missile→missiles.msg, Projectile→projectiles.msg, Torpedo→torpedoes.msg, Expendable→expendables.msg.)

### Enum values (2026-08-16, decoded from game scripts + live testing)

Bit-flag layouts, verified numerically:

| Enum | Values |
|------|--------|
| `BaseCategory` | Nothing=0, Air=1, Surface=2, Subsurface=4, Land=8, Space=16, All=31 |
| `ElementCategory` | Nothing=0, Submarine=1, Ship=2, Aircraft=4, LandElement=8, Biologic=16, Projectile=32, Bomb=64, Missile=128, Torpedo=256, Expendable=512, Explosion=1024, SpaceElement=2048, Camera=4096, Sensor=8192 |
| `AttackRanges` | None=0, Short=1, Medium=2, Long=4 |
| (launcher `_AttackSide`) | enum fields: Fore / Aft / Starboard / Port (implied ordering; explicit ints not emitted) |

**This explains the whole categorization algebra:** `CollectFlags(MountedCategory)` iterates `Enum.GetValues(ElementCategory)` and keeps every `elementCat` where `(mountedCat & elementCat) == elementCat` — so it yields the launcher's ElementCategory flag(s) (Missile=128, Projectile=32, Torpedo=256, Expendable=512). The BaseCategory set is then derived from the **mounted weapon's DB `TargetCategory`**: `Core.Select(elementCat, MountedDatabaseID).TargetCategory`, AND-ed against each `Enum.GetValues(BaseCategory)` value in the `_BaseCategoryCategorized` build. E.g. a Type-87 rack (`MountedCategory` Projectile/32, dbid 99992902) selects `TargetCategory=4` → matches Subsurface; a YJ-83 launcher (Missile/128, 541) selects `TargetCategory=2` → matches Surface. `AttackRanges` mirrors `DetermineWeaponRange` (Short=1, Medium=2, Long=4 as the range-check yields).

**`SLauncher.sav` field order CONFIRMED (2026-08-16, from save data analysis):** `[0]=SnapshotSMRI (uint)` · `[1]=RefSMRIs (list<uint>)` · `[2]=_MountedSlots (dict<int,int>)` · `[3]=_CurrentLauncherMag (int)` · `[4]=_LauncherIdx (uint)` · `[5]=_MountedCategory (int)` · `[6]=_MountedDatabaseID (double)` · `[7]=_LauncherStatus (int)` · `[8]=_WiredWeaponSMRI (int)`.

So my earlier "cat" field (values -2/0/1/5) is **`_CurrentLauncherMag`** (ammo loaded in that launcher; -2/0 = empty, 1 = single munition, 5 = e.g. depth-charge rack), and the earlier "rng" field (32/128/256/512) is **`_MountedCategory`** — the `ElementCategory` bit flags (Projectile=32 / Missile=128 / Torpedo=256 / Expendable=512). `_LauncherStatus`: 2 = tube loaded & ready, 0 = empty. `_WiredWeaponSMRI` = -1 = none wired.

**Launcher class vs `_MountedCategory`:** `Launcher.LoadSnapshot` reads `sl._CurrentLauncherMag` → `this._CurrentLauncherMag`, `sl._WiredWeaponSMRI` → `this._WiredTorpedoSMRI`, then validates `sl._MountedCategory` is a single-bit (power-of-two) flag, calls `SetMountedElement(sl._MountedCategory, sl._MountedDatabaseID)`, copies `sl._LauncherStatus` → `_TubeStatus`, and returns early (empty) unless the object is a `RocketLauncher`/`ArtilleryLauncher`/`TorpedoLauncher` subclass. The actual mountable `MountedCategory` comes from the platform/launcher data inside the `.core` ZIP, not from `Arsenal` mission wiring.
